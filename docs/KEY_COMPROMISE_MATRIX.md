# CryptoFlex Key-Compromise Matrix

Every row below is based on reading the actual current implementation (`api.py`, `keystore.py`, `ephemeral.py`) at the time this document was written, not on assumed/idealized behavior. If the code changes, this matrix must be re‑verified against it, not just re‑derived from memory.

| Secret compromised | What becomes recoverable | What does NOT become recoverable | Source |
|---|---|---|---|
| **Long‑term static private key** (from `establish_keys()`, used for file encryption via `encrypt()`/`decrypt()`/streaming) | Every past AND future ciphertext encrypted to the corresponding static public key, for as long as that keypair remains in use. This is expected, inherent behavior for a static‑identity encryption scheme (the same trade‑off `age`'s identity‑file mode makes) - it is not a bug. | Ciphertexts encrypted to a *different* keypair, even one belonging to the same application/user, are unaffected. | `api.py`'s `establish_keys()`/`derive_root_key()`/`recover_root_key()` - no forward secrecy is claimed or provided for this path; see `ephemeral.py`'s own module docstring for the explicit contrast with the ephemeral path. |
| **A single ephemeral session key** (`establish_ephemeral_keys()`, one message via `ephemeral_encrypt()`) | Only that one message. The ephemeral private key is generated fresh and discarded immediately per the source's `encapsulate()` implementation. | All other past and future messages, including other messages to the same recipient, since each uses independently generated ephemeral randomness. | `ephemeral.py` module docstring: "each message should use fresh ephemeral keys that are discarded immediately after use." |
| **Recipient's long‑term static private key, in the ephemeral messaging mode** | Every PAST ephemeral message that was ever sent to that recipient, if an attacker also recorded the ciphertexts (the sender's ephemeral public key is stored in‑clear in each message's header, so a recorded past ciphertext plus the now‑compromised recipient static key is sufficient to redo the DH and recover that message's root key). This is the specific, explicit limitation `ephemeral.py` documents. | Nothing about *future* messages is protected either, until/unless the recipient rotates their static keypair - this mode does not provide protection against this specific compromise at all; it only prevents *sender‑side* ephemeral‑key reuse across messages. | `ephemeral.py` module docstring, verified verbatim: "this ... does not provide full forward secrecy against later compromise of the recipient's long-term private key." |
| **Keystore password** (used to decrypt a saved `KeySet` via `keystore.py`) | The static private key(s) that password protects, and transitively everything in the "long‑term static private key" row above. | Nothing beyond what compromising the underlying static private key itself would already expose - the password is a second factor protecting storage, not an independent secret with its own separate blast radius. | `keystore.py`: Argon2id (default) or Scrypt N=2^17 (legacy) protects the serialized private key material; compromising the password gives an attacker exactly what compromising the raw stored private key file would. |

## What this matrix does not cover

- **Native‑memory‑level compromise** (an attacker with the ability to read process memory directly, e.g. via a coredump or compromised host) is a different threat class from "knows a password" or "has a file" - see `docs/THREAT_MODEL.md`'s existing zeroization‑scope discussion for what is and isn't defended against at that layer.
- **This is not a formal compromise‑and‑recovery proof.** It is a plain‑language description of what the current code does, verified by reading it, not a cryptographic analysis of whether these are the *only* consequences of each compromise.
